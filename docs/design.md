# Multi-Account MCP

> Claude から同じサービスの複数アカウント（Google の個人用と仕事用など）を同時に使うための、自分専用 MCP サーバー

## 解決したい課題（Problem）

Claude のコネクタは1サービスにつき1アカウントしか繋げない。
Google の個人用と仕事用のように、同じサービスで複数のアカウントを持っていると、片方しか Claude から使えない。

## ターゲットユーザー

自分専用。同じサービスに複数アカウントを持ち、Claude Code や Claude Desktop を日常的に使う人。

## コア体験（Core Experience）

**どのアカウントのファイルかを気にせずに頼める**こと。

- 作業中にコネクタを繋ぎ直さなくていい
- 「このスプシを直して」と言えば、そのファイルにアクセスできるアカウントで勝手に開く

きっかけの例（2026-10）：コネクタは個人用に繋いでいたが、仕事用の作業報告書のスプシの修正を Claude に頼んだら「アクセス権が無い」と言われた。

## ソリューション概要

複数アカウントの接続に対応した MCP サーバーを自前で用意する。

- **まずは Google から始め、他のサービスは後から足せる作りにする**
- **手元で動かすローカル MCP にする**（スマホは使わず、普段使うのは Claude Code と Claude Desktop のため）
- 最初の組み合わせは **個人用と仕事用の Google アカウント**。対象は **Drive と Sheets**
- **アカウントは自動で解決する**（ユーザーにも Claude にも普段は選ばせない）
  - ファイル ID・URL での操作：アクセスできるアカウントを順に試し、どのファイルがどのアカウントかを覚えておく
  - 検索：全アカウントを横断し、結果にアカウント名を付けて返す
  - `account` 引数は、明示したいときだけ使う任意の引数にする
  - 新しいファイルを作るときは、次の順で決める。既定のアカウントは置かない
    1. 作る先のフォルダが指定されている → そのフォルダがあるアカウント
    2. 既存のファイルを元にしている（コピー・「同じ場所に」など）→ 元のファイルのアカウント
    3. どちらでもない → ツールがエラーを返し、Claude にユーザーへ聞かせる
- 1つのタスクでアカウントをまたぐ操作は、今は想定しない
- **権限は `drive`（フルアクセス）＋ `spreadsheets`**。ファイルの作成・削除も Claude にさせるため
  - 強い権限を持つ分、**ツールの側で絞る**
  - 削除はゴミ箱への移動だけにする（30日以内なら戻せる）。完全削除のツールは作らない
  - 共有設定を変えるツールは作らない（外部への漏えいを防ぐ）
  - ツールを危険度ごとに分ける（読む／書く・作る／削除）。Claude Code の permissions で、読むツールは自動許可、削除は毎回確認、のように設定できるようにする
  - 削除などのツールには MCP の `destructiveHint` を付ける
- **最初のバージョンのツール**（足りないものは使いながら足す）

  | 段 | ツール | すること |
  |---|---|---|
  | 読む（自動で許可） | `list_accounts` | 繋がっているアカウントの一覧 |
  | | `drive_search` | 全アカウントを横断して検索。結果にアカウントのラベルを付ける |
  | | `drive_read` | ファイルの中身を読む（Google ドキュメントはテキストにして返す） |
  | | `sheets_read` | スプシのセルの値を読む |
  | 書く・作る | `sheets_write` | セルの値を書き換える |
  | | `sheets_append` | 行を末尾に追加する |
  | | `drive_create` | ファイル・スプシ・フォルダを作る（作り先は上のルールで決める） |
  | | `drive_copy` | ファイルをコピーする |
  | | `drive_rename` | 名前を変える |
  | 削除（毎回確認） | `drive_trash` | ゴミ箱へ移す |

  - 後回し：`drive_move`（フォルダの移動）、Google ドキュメントへの書き込み（Docs API と追加の権限が要る）
- **トークンは 1Password に置く**
  - リフレッシュトークンと OAuth クライアントのシークレットを、専用の保管庫に置く
  - `op` は承認が10分で切れ、呼ぶたびに Touch ID を求めるので、**最初にツールが使われたときに1回だけ読み、あとはメモリに持つ**
  - アクセストークン（1時間で切れる）はメモリの中だけで更新し、1Password には書き戻さない
  - 1Password に書くのは `login` のときだけ
  - 体験：Claude Code のセッションで最初に Drive を触ったとき、Touch ID を1回求められる（勝手に使われないための関所にもなる）
- **アカウントの追加・削除は CLI で行う**
  - `login`：ブラウザで Google のログイン画面を開き、終わったらトークンを 1Password に保存する
  - `logout`：トークンを Google 側で取り消してから、1Password から消す
  - MCP サーバー本体はログインの画面を持たず、保存済みのトークンを読むだけ
- **インストールと登録**
  - リポジトリを ghq で clone してビルドする。npm には公開しない
  - `register`：mise で入れた Node の絶対パスを調べて、Claude Code（ユーザースコープ）と Claude Desktop の設定にサーバーを登録する
  - Node を更新したときや Mac を買い替えたときは、`register` を打ち直す
  - `unregister`：Claude Code と Claude Desktop の設定から登録を外す
- **ログ**
  - 操作の記録を `~/Library/Logs/multi-account-mcp.log` に残す。書く・作る・削除のツールが呼ばれるたびに、日時・ツール名・アカウント・ファイル ID とファイル名・成否を1行で書く
  - トークン、ファイルの中身、セルの値は書かない
  - デバッグ用の出力は標準エラー出力へ（標準出力は MCP の通信に使うので書かない）。Claude Desktop はこれを自分のログに保存する
  - ローテーションはせず1ファイルのまま。1日200回操作しても1年で15MB程度のため。大きくなりすぎたら見直す
- 中身を3層に分け、サービスの追加とリモート化のどちらにも対応できるようにする

```
[通信の層]    stdio（ローカル） / Streamable HTTP（リモート）   ← ここだけ差し替え
[共通の層]    アカウント台帳・トークン保管・ツールの登録
[サービス層]  google/ （認証方法 + ツール群）、 将来ほかのサービスを追加
```

## 想定技術スタック

| レイヤー | 技術候補 | 備考 |
|---------|---------|------|
| 通信 | MCP（stdio） | リモート化するなら Streamable HTTP に差し替え |
| 実装言語 | TypeScript | 公式 MCP SDK が一番成熟。ランタイム（Node）は mise で入れる |
| Google API | `@googleapis/drive`, `@googleapis/sheets` | 巨大な `googleapis` は使わず、必要な API だけに絞る |
| 認証 | Google OAuth（アカウントごと） | |
| トークン保管 | 1Password（`op` CLI、専用の保管庫） | 秘密情報は 1Password に集約する方針に合わせる。保管場所は差し替えられる作りにする |
| 設定ファイル | `~/.config/multi-account-mcp/` | アカウント一覧と「ファイル→アカウント」の記録だけ。秘密情報は書かない |
| その他 | | |

## 競合・代替手段

複数アカウントに対応した Google 向けの OSS の MCP サーバーはすでにある（2026-10-31 時点、中身は未検証）。

| OSS | 対象 | アカウントの指定 |
|---|---|---|
| [bakissation/mcp-google-multi](https://mcpservers.org/zh-CN/servers/bakissation/mcp-google-multi) | Drive, Sheets | 短い別名で指定。アカウント間のファイル移動ツールあり |
| [aaronsb/google-workspace-mcp](https://glama.ai/mcp/servers/aaronsb/google-workspace-mcp) | Gmail, Calendar, Drive | ツール呼び出しごとにメールアドレスで指定 |
| [@mindstone/mcp-server-google-workspace](https://socket.dev/npm/package/@mindstone/mcp-server-google-workspace) | Drive, Sheets ほか | アカウント設定ファイル＋アカウントごとの認証情報 |
| [taylorwilsdon/google_workspace_mcp](https://glama.ai/mcp/servers/@taylorwilsdon/google_workspace_mcp/blob/04b9ae027c9180b9f6def7a0b7ec2bbd603acd14/README.md) | Drive, Sheets ほか多数 | 複数アカウント対応かは未確認 |

見た範囲では、どれも **アカウントを明示して指定する** 方式。コア体験の「アカウントを自動で解決する」はなさそうで、ここが自作する理由になりうる。

**結論：自作する。** OSS は中身の実装が見えにくく、Google の2アカウント分の権限を預けるにはセキュリティ面で信用しきれない。自作ならすべてを自分で管理できる。

## 懸念点・リスク

- ~~仕事用 Google アカウントの Workspace が外部の OAuth アプリを許可していないと繋がらない~~ → 管理者は自分で、外部アプリのルールもないので問題なし
- 自作の OAuth アプリを「テスト中」のままにすると、リフレッシュトークンが7日で失効する
  - 対処案：OAuth アプリを「外部」かつ「本番」にする（審査は受けない）。未審査アプリの警告画面は出るが、100 ユーザーまでなら使え、トークンは7日で切れない
  - 仕事用の Workspace 側では、管理コンソールでこのアプリを「信頼済み」にしておく
  - 本番化の前に発行したトークンは7日の期限を引き継ぐので、本番化してからログインし直す
- ローカル MCP はブラウザの claude.ai からは使えない
- **要調査**：Claude Desktop から起動したプロセスで、`op` の Touch ID 承認がちゃんと出るか（実装の最初に試す）
- ~~開発環境を Dev Container にするか~~ → Dev Container の例外にし、Mac の上で直接開発する。Mac を汚さないための対策は `docs/decisions.md` の 20
- Mac を買い替える・OS を入れ直す場合
  - トークンは 1Password で同期されるので、`login` し直さずに使える（同期されていなくても、`login` をやり直せば新しいトークンが発行される）
  - 新しい Mac でやるのは、コードの clone とビルド、`op` CLI のセットアップ、`register` の3つだけ
  - 「どのファイルがどのアカウントか」の記録はキャッシュなので、なくなっても使ううちに作り直される
  - 古い Mac のトークンは、取り消すまで有効なまま残る。手放す前に Google アカウントの「サードパーティ製のアプリとサービス」から接続を解除する（`logout` コマンドで取り消せるようにしておく）
